# 14 — Core Utility Layer

## Why this is its own layer, and why it's built before any AI module

`02-folder-structure.md` already places `src/lib/` alongside `src/modules/`, but only specified three files (`portableText/`, `slug.ts`, `json.ts`, `tokenCount.ts`) because those were the only utilities a v1 reading of the module list surfaced. At commercial scale, the number of small, provider-independent, pure-logic needs grows faster than the module count — every module tends to need two or three of these, and if they're written ad hoc inside whichever module first needed them, the second module that needs the same thing either duplicates the logic (drift risk) or reaches into another module's folder (the exact tight-coupling `02-folder-structure.md`'s "a module never imports from another module's folder" rule exists to prevent).

**The hard rule for this layer, stated once so it governs everything below:** every file in `src/lib/` must be import-able and testable with **zero** network calls, zero provider SDK imports, and zero Sanity/Sheets client imports. If a "utility" needs any of those, it isn't a utility — it belongs in `src/providers/` or `src/integrations/`. This is the same discipline `09-provider-abstraction.md` applies to LLM calls, applied here to everything else: keep pure logic pure, keep I/O at the edges.

## Utility inventory

| `lib/slug.ts` | Canonical slugify (exact algorithm from `seed-meta.ts`) + collision-suffix strategy (`-2`, `-3`, …). Already specified in `02-folder-structure.md`; unchanged. | nothing |
| `lib/filename.ts` | **NEW.** Deterministic, collision-safe filename generation for uploaded images/assets (e.g. `hotel-room-matrix-<shortHash>.jpg`) — needed once Image Upload (module 14) and any future non-image file upload exist, and was previously left as ad hoc logic inside the Image Upload module. Extracting it means the same "safe filename from arbitrary text" logic is available to any future asset-producing module (video thumbnails, podcast cover art — see `18-scalability-and-future-features.md`) without duplicating it. | `lib/slug.ts` (reuses the same sanitization core) |

| `lib/imageHelpers.ts` | **NEW.** Pure image-metadata helpers: reading dimensions/content-type from a buffer, validating a buffer is a real, non-empty, accepted image format before it's handed to Sanity's asset upload (this is the concrete implementation behind Image Generator's "returned image byte size > 0 and content-type is an accepted image format" validation rule in `03-module-flow.md`, previously described but not given a home). | `lib/retry.ts` | **NEW, extracted.** The exponential-backoff-with-jitter primitive that `08-retry-strategy.md` describes conceptually as living inside `core/moduleRunner.ts`. | `lib/prompts.ts` | Prompt-file loading, partial resolution, interpolation — the mechanics layer underneath the Prompt Registry (`13-prompt-management-system.md`). Renamed conceptually from a bare helper to "the thing the registry is built on," not a separate concern. | `lib/cache.ts` (for the file-read cache) |

| `src/logging/logger.ts` | Structured logger. Already specified. Stays in `src/logging/` (it has a genuine side effect — writing log output — so it's not a pure `lib/` function, but it has the same zero-provider-dependency rule). | nothing |

## What changed vs. the original `02-folder-structure.md` listing

The original document under-specified this layer — it named `portableText/`, `slug.ts`, `json.ts`, `tokenCount.ts` and stopped, because at the time no module had yet surfaced the need for `filename.ts`, `markdown.ts`, `dates.ts`, `fileHelpers.ts`, `imageHelpers.ts`, `retry.ts`, or `cache.ts` as *shared* concerns rather than module-internal logic. Building this layer explicitly, before any AI module, converts "logic that would otherwise be duplicated or ad hoc across 3–4 modules each" into "logic written once, tested once, imported everywhere." `02-folder-structure.md` is updated (see that file) to reference this document as the authoritative utility inventory rather than re-listing a shorter, now-stale set inline.

## Ordering implication for the build roadmap

Because every AI module's `validate.ts` depends on `lib/schemaValidator.ts`, and several modules' core logic depends on `lib/markdown.ts`/`lib/dates.ts`/`lib/retry.ts`/`lib/cache.ts`, this entire layer must exist **before** the first AI module is built — this is reflected in the revised build order in `12-future-roadmap.md` (Core Utilities moves ahead of Provider Layer and AI Modules, per the user's preferred phase ordering, with the reasoning for *why* that ordering is correct laid out in this document's dependency list above, not just asserted).

## Testing implication

Every file in this layer is a pure function or a small, dependency-free class (the cache, at most, holds process-lifetime state — no I/O beyond what's explicitly named, like `fileHelpers.ts`'s disk writes). This makes the utility layer the **highest test-coverage-to-effort ratio** code in the whole system — no mocking required for the majority of these files (`slug.ts`, `markdown.ts`, `dates.ts`, `retry.ts`'s backoff math, `schemaValidator.ts`), and where a real dependency exists (`fileHelpers.ts` touching disk), it's Node's own `fs` module, trivially fakeable with an in-memory filesystem library if needed. `10-testing-strategy.md`'s "near-exhaustive edge-case coverage" expectation for deterministic modules is extended to this entire layer, not just the Portable Text converter it originally called out.
