# 12 — Future Roadmap & Implementation Order (revised)

> **Revision note:** Part 1 (deferred post-v1 features) is unchanged in substance, with a few cross-references added to the six new documents (`13`–`18`) that now formalize mechanisms it previously only gestured at. Part 2 (build order) is substantially revised to adopt the user's preferred 12-phase philosophy as the primary structure — this section explains where that order is followed as given, where it's an improvement over the original roadmap's ordering, and where a small clarifying refinement is folded in without changing the phase order itself.

## Part 1 — Post-v1 roadmap (what's deliberately deferred)

| Feature | Why deferred | Trigger to build it |
|---|---|---|
| Prompt A/B testing / variants | Adds real complexity (experiment assignment, result tracking) with no payoff until there's enough run volume for statistically meaningful signal. **The mechanism is now designed, not just gestured at** — `13-prompt-management-system.md`'s inheritance/override resolution chain generalizes to a `variantId` axis with no new architecture, only new content once built. | Monthly post volume high enough (roughly 50+/month) for a prompt change's effect to be measurable. |
| LLM-as-judge output-quality eval harness | v1 already has Technical Review + SEO Review + QA Gate as in-pipeline quality gates. | Prompt iteration velocity increases enough that manual review of every change becomes the bottleneck. |
| Provider batch-API scheduling for backlog catch-up | Only pays off at real backlog volume; adds async-polling complexity not worth it for steady-state one-row-at-a-time operation. | A backlog of 20+ pending Sheet rows accumulates, or an overnight catch-up job is requested. |
| Swapping `stateStore` from local JSON to a real database | Local JSON is sufficient for single-machine, low-concurrency operation. **Now has a named, concrete trigger** — `18-scalability-and-future-features.md` identifies this as the exact point where multi-tenant data isolation becomes a real requirement, not a vague "someday." | Concurrent-run volume grows past safe local-file locking, or true multi-tenancy is built. |
| A full interactive cost/metrics dashboard | **Partially superseded** — `15-cost-tracking-system.md` already builds the Cost Reporter (per-run and per-date-range report generation) as a v1 capability, not deferred. What remains deferred is only a persistent, queryable *UI* on top of that data — the data and the reporting *function* already exist. | Enough run history accumulates that a UI beats reading Cost Reporter output directly. |
| On-demand Sanity revalidation webhook (Blogspage Agency-side) | Cannot be built by this project — read-only contract. Documented as a flagged dependency, mirroring `knowledge/recommended-improvements.md` item 3. | If/when the user separately modifies Blogspage Agency to add this. |
| Multi-post-type support (newsletter, social, video/podcast scripts) | v1's modules are designed reusable, but building a second consumer before the first is proven would be premature. **Now analyzed in depth** — `18-scalability-and-future-features.md` gives an honest accounting of what's free (Research/Planner/SEO Planner's structure) vs. genuinely new work (new Content Planner variants, new review criteria) for each content type. | The blog pipeline is stable in production and a second real use case exists. |
| Automated new-category creation | Explicitly flagged in `automation-integration.md` as a content decision, not a technical stub — v1 restricts to the four seeded categories. | If category-mismatch routing becomes frequent enough that the user wants to revisit the restriction. |
| Streaming provider responses | **Explicitly rejected for this pipeline, not a default deferral** — `09-provider-abstraction.md`'s Phase 4 pre-implementation revision names this directly: this is a backend automation pipeline with no human watching a live token stream today, and streaming only improves *perceived* latency, which has no audience here. Listed in this table only so the decision and its reasoning are recorded, not because it's expected to be revisited on a timeline. | A live-progress dashboard or other human-in-the-loop-during-generation UI becomes a real, named feature request — at which point it is an additive second method on `LLMProvider`, not a redesign. |
| Automated provider failover / circuit-breaking on health signals | `09-provider-abstraction.md`'s Phase 4 pre-implementation revision adds the `ProviderStatus`/`ProviderHealthReporter` interface now, deliberately ahead of any consumer, so this feature has a stable interface to build against later instead of retrofitting health tracking into five adapters at that point. No orchestration logic (failover routing, circuit-breaking, alerting) is built in Phase 4. | A real reliability incident (a provider outage affecting a production run) makes automatic failover worth the added orchestration complexity, rather than building it speculatively before any incident has shown it's needed. |

## Part 2 — Implementation roadmap: build order

### The user's requested philosophy

> 1. Foundations · 2. Prompt System · 3. Core Utilities · 4. Provider Layer · 5. Sanity Integration · 6. PipelineState · 7. Orchestrator · 8. AI Modules · 9. Media Pipeline · 10. Publishing · 11. Notifications · 12. Optimization

### Assessment: adopted, with one credited improvement and three folded-in refinements

**This order is adopted as the primary build sequence.** It is not just acceptable — in one specific respect it is a genuine improvement over the original roadmap's ordering, and that improvement is worth naming precisely rather than silently accepting it:

**Why Prompt System (2) and Core Utilities (3) before Provider Layer (4) is better than the original ordering:** The original roadmap built the Provider Layer first (its old Phase 1) and proved it with "a trivial prompt" hardcoded inline, because nothing else existed yet to load a real one from. Under the user's order, by the time Provider Layer is built (phase 4), the Prompt Registry (phase 2) already exists — so Provider Layer's first real smoke test can call `providerFactory.getProvider('CHEAP', config).complete(...)` using an **actual prompt loaded through the real registry** (e.g., `prompts/research/system.md`), not a throwaway inline string. That's a more realistic, higher-value first integration test, and it falls out naturally from this ordering rather than needing to be engineered specially. Neither the Prompt Registry (file loading, resolution, interpolation) nor the Core Utility layer (pure functions by `14-core-utilities.md`'s own hard rule) has any dependency on `LLMProvider` existing — so there is no hidden blocker to building them first, and doing so pays off exactly as described.

**Why PipelineState (6) after Sanity Integration (5) works, with one clarification needed:** This ordering is sound *provided* "Sanity Integration" (phase 5) is read as **the raw adapter layer only** — `sanityWriteClient.ts`, `sanityReadClient.ts`, `seedRefs.ts` — none of which reference `PipelineState` at all; they take a generic document object or query string as a parameter. The Sanity Document Builder and Publish *modules* (which do read/write specific `PipelineState` sections per `04-json-contracts.md`'s ownership table) correctly wait until `PipelineState` is formalized in phase 6 and built out as real modules later, in phase 10 ("Publishing"). Read this way, there's no ordering problem — the clients don't need the schema, and the modules that do need it wait for it. This clarification is stated explicitly here so it doesn't have to be inferred.

**The three refinements below are folded into the named phases, not inserted as new phases** — the user's 12-phase structure and phase order is preserved exactly as given.

### The revised 12 phases

**1. Foundations** — `core/types.ts` (skeleton — the full nested schema is completed in phase 6, but error classes and config need *some* shared vocabulary to exist), `core/errors.ts` (the four error classes, `07-error-handling.md`), `src/config/env.ts`/`models.ts`/`pipeline.ts`, `src/logging/logger.ts`. *Demoable:* typecheck passes, config loading fails loudly and correctly on a missing required env var.

**2. Prompt System** — `src/prompts/registry.ts` (the Prompt Registry, `13-prompt-management-system.md`), `lib/prompts.ts`'s loading/partial-resolution/interpolation mechanics, `lib/cache.ts` (the process-lifetime file cache the registry sits on). Every prompt file for every module can be authored and unit-tested (snapshot tests on interpolation, per `10-testing-strategy.md`) at this point, with zero real prompts having been used in an actual model call yet. *Demoable:* `promptRegistry.get('writer', vars)` returns a fully-assembled, correctly-interpolated `PromptSet` for every module, verified by snapshot test, no provider involved.

**3. Core Utilities** — the full inventory from `14-core-utilities.md`: `lib/slug.ts`, `lib/filename.ts`, `lib/readingTime.ts`, `lib/markdown.ts`, `lib/json.ts`, `lib/schemaValidator.ts`, `lib/dates.ts`, `lib/tokenCount.ts`, `lib/fileHelpers.ts`, `lib/imageHelpers.ts`, `lib/retry.ts`. **Refinement folded in here:** `lib/portableText/fromMarkdownAst.ts` and `lib/portableText/validatePortableText.ts` are built and hardened in *this* phase, against hand-written Markdown fixtures covering every Portable Text block type in `knowledge/automation-integration.md` (paragraph, heading, decorators, external/internal link, list, blockquote, image, code block, CTA) — not deferred to phase 10. This preserves the original roadmap's reasoning for front-loading this specific piece of logic (it's the highest subtle-bug-risk deterministic code in the system, and per `14-core-utilities.md`'s own classification it *is* core-utility-layer code — provider-independent, pure-function, belonging in `src/lib/`) without moving it out of the phase where it already structurally belongs. What's deferred to phase 10 is only the **module** that wires this utility to real `PipelineState` (registry key `portable-text`), not the underlying conversion/validation logic itself. *Demoable:* feed a hand-written Markdown fixture in, get out Portable Text that passes every structural invariant Blogspage Agency's own schema enforces — plus every other utility at full, near-exhaustive test coverage per `10-testing-strategy.md`'s expectation for this layer.

**4. Provider Layer** — `LLMProvider`/`ImageProvider` interfaces (`09-provider-abstraction.md`), `AnthropicProvider.ts` (built first, as the grounded-pricing baseline per `06-cost-optimization.md`), `providerFactory.ts`, `FakeLLMProvider` (built immediately after the real adapter, so every module from phase 8 onward can be unit-tested from day one). *Demoable:* a smoke-test script gets a real completion from Anthropic **using a real prompt loaded via the phase-2 registry** — the concrete payoff of this ordering, named above.

**5. Sanity Integration** — `integrations/sanity/sanityWriteClient.ts`, `sanityReadClient.ts`, `seedRefs.ts` — raw adapter code, no `PipelineState` dependency, per the clarification above. **Refinement folded in here:** run a smoke test that hand-constructs a fixture document using `knowledge/automation-integration.md`'s own worked JSON example (not a `PipelineState`-derived one — that doesn't exist yet) and confirms it publishes successfully to a **Sanity sandbox dataset**, including exercising the slug-uniqueness/idempotency logic described in `07-error-handling.md`. This retires the "is writing to Sanity actually safe" risk before any content-generating code exists, without requiring `PipelineState` or the Document Builder module — both of which are still phases away. *Demoable:* a hand-crafted fixture document publishes to the sandbox dataset, is verifiably fetchable, and a deliberate slug collision resolves correctly via the numeric-suffix strategy.

**6. PipelineState** — the full nested schema from `04-json-contracts.md`: every section (`metadata`, `brief`, `research`, `planning`, `seo`, `draft`, `review`, `qa`, `images`, `sanity`, `publishing`, `metrics`, `errors`, `timings`), the zod runtime schemas backing them, and the ownership table encoded as a lint/type-level check where practical (e.g., a module's declared write-section is checked against what it actually returns). Built now, with real knowledge of what phase 5's Sanity client actually needs in a document (informing `sanity.document`'s shape with confidence, not speculation) and what phase 2–4 already established about prompts and providers (informing `metrics.costEvents`' shape directly from `LLMCallResult`, per `09-provider-abstraction.md`'s revised interface). *Demoable:* every sub-type in `04-json-contracts.md` compiles and validates against a hand-written fixture state; the contract-test suite (`tests/contract/`) has real types to check module-boundary compatibility against, for the first time.

**7. Orchestrator** — `core/stateStore.ts` (persist/reload, now writing into `storage/state/` per the revised `02-folder-structure.md`), `core/moduleRunner.ts` (retry wrapper, `08-retry-strategy.md`, now also the emission point for `CostEvent`s per `09-provider-abstraction.md`'s revision), `core/orchestrator.ts`. **Refinement folded in here:** prove resumability and state-persistence mechanics on a **trivial stub pipeline** (a fake Sheet Reader → a fake Sanity Document Builder → a fake Publish, all deterministic/no-op) before any real module is wired in — the same reasoning the original roadmap applied to its own orchestrator phase, preserved here without changing where it sits in the user's order. *Demoable:* a trivial run persists state at every step and resumes correctly if killed mid-run; `moduleRunner` correctly emits a `CostEvent` and an `ErrorRecord` even for a fake/no-op module call, proving the plumbing works before it's asked to handle a real provider response.

**8. AI Modules** — every content-producing module through the review loop, built and wired to the now-real orchestrator in this order: `sheet-reader` (the pipeline's entry point — real Google Sheets integration, replacing phase 7's stub) → `research` → `planner` → `seo-planner` → `writer` → the review loop (`reviewer-technical`, `reviewer-seo`, `humanizer`, `qa`, `improver`, plus the orchestrator wiring for the bounded loop and its termination-condition tests). Each module is unit-tested with `FakeLLMProvider` before being wired in, then the research-through-planning chain is run once against real `STANDARD`/`PREMIUM` providers with a real topic brief and manually quality-reviewed — the first point in the build where prompt *quality*, not just code correctness, becomes a real variable. *Demoable:* a full, reviewed, humanized article draft, with the review loop correctly bounded and correctly routing to `needs_review` on a deliberately-bad fixture.

**9. Media Pipeline** — `image-planner` → `image-generator` (with the parallel-execution wiring from `17-module-dependency-diagram.md`) → `image-validator` → `image-upload` (real Sanity asset upload, exercising the sandbox dataset already proven safe in phase 5), plus the bounded image-loop wiring and its own termination tests. *Demoable:* real generated, validated, uploaded images for a real article, with a deliberately-bad image prompt correctly triggering retry-then-degrade.

**10. Publishing** — `internal-links` → `portable-text` (wiring the phase-3 utility to real `state.draft.current`/`state.sanity.resolvedLinks`/`state.images.uploaded` — low-risk by design, since the hard conversion logic was already hardened in phase 3) → `faq-generator` → `structured-data-check` → `sanity-builder` (wiring the phase-3-adjacent assembly logic to real pipeline data, informed by phase 5's already-proven write path) → `publish` (wired to real data, exercising the idempotency check phase 5 already validated against a fixture). *Demoable:* one full, real, end-to-end-generated Sanity document, published — first against the sandbox dataset.

**11. Notifications** — `notify` (Slack/email), and the Cost Reporter (`src/reporting/costReporter.ts`, `15-cost-tracking-system.md`) wired to produce the real per-run report attached to every notification, now meaningful for the first time because every module it reports on is real. *Demoable:* a `published` run and a deliberately-forced `needs_review` run each produce a correct, complete Notification with an accurate cost breakdown attached.

**12. Optimization** — the sandbox integration test (`tests/integration/fullPipeline.sandbox.test.ts`) run for real for the first time end-to-end; load-testing concurrency limits (`11-performance.md`) against real provider rate limits; running a batch of real topic briefs through the pipeline and tuning prompts based on real output; reconciling actual `CostEvent` data against the estimates in `06-cost-optimization.md` and correcting any tier assignment that isn't earning its cost; then — as a deliberate, explicitly-confirmed final step, never an automatic phase completion — cutting over from the sandbox dataset to the real production Sanity dataset.

## Why this synthesis is correct

Every phase in the user's requested order is preserved exactly as named and exactly in sequence — nothing was reordered. What changed from a literal reading of the twelve names is only that this document now says precisely what "Sanity Integration" and "AI Modules" mean at the boundary between phases (raw adapters vs. schema-dependent modules; content modules starting from the pipeline's real entry point), and folds three specific, previously-identified risk-mitigation steps (Portable Text hardening, Sanity write-path safety, orchestrator resumability) into the phases where they structurally belong rather than either dropping them or inventing new phases to hold them. The one place this document actively argues the user's order is *better* than the original roadmap's — Prompts and Utilities preceding the Provider Layer — is stated as a specific, falsifiable claim (a more realistic first integration test) rather than blanket agreement.

## Productization pass (2026-09-11) — what changed and what didn't

This roadmap's Part 2 remains the authoritative module-level build order. The **productization pass** folded in three new requirements as architecture — not as new phases stacked on the twelve: **reselling/multi-client configuration** (`20-product-reselling-architecture.md`), **hard cost-budget modes and human-in-the-loop checkpoints** (`21-cost-budget-modes-human-in-loop.md`), and the **re-prioritized execution plan** below. The twelve phases themselves are unchanged; their inputs (Prompt System, Core Utilities, Provider Layer) and outputs (Sanity Integration, the module layers) now all carry profile-gated config from the start.

### Revised execution plan (supersedes the original phase ordering for the remaining work)

1. **Architecture (the productization pass itself)** — `20` and `21`, plus the consistency edits across `01`–`04` and `06`. *(This document set — done.)*
2. **Existing build** — implement the new seams into what already exists: `src/config/profiles.ts` (Client Profile types + budget presets), `Config`/`metadata.clientProfileId`, `awaiting_assets` status + `images.staged` in `core/state.ts` (schema + ownership + tests), CLI `--profile` + `attach-images` gateway, `validateConfig` profile checks.
3. **Pending development** — the previously-planned remaining phases (review loop, media, publishing, notifications, optimization), built **config-gated from day one** so `imageSource`, `runSet`, and `approvals` are values, not refactors: manual-image flow → minimal publish path → quality layers → integration test + budget verification → sandbox→production cutover.

To the twelve phases themselves: nothing in the ordering is invalidated — the productization pass is a *cross-cutting configuration layer*, not a reordering of module dependencies (`17-module-dependency-diagram.md` remains the graph).
