# Slug System

## Two independent slug mechanisms exist — do not conflate them

### 1. Sanity Studio slugs (`post`, `category`, `author`)

Generated by Sanity's built-in `slug` field type with `options.source`
(`title` for post/category, `name` for author). Sanity's default slugifier is
used inside Studio — it lowercases, strips diacritics, and hyphenates.
`post.slug` also sets `options.maxLength: 96` and a uniqueness check
(`context.defaultIsUnique`).

For **programmatic document creation** (bypassing the Studio UI — i.e. what
an automation does), you must construct the slug value yourself in the
document JSON as `{ "_type": "slug", "current": "the-slug" }` — Sanity does
not auto-slugify a `title` string on write; the `slug` type is just a plain
object field with no server-side derivation. See the project's own
`seed-meta.ts` slugify function as the canonical algorithm actually used:

```ts
function slugify(value: string): string {
  return value
    .toLowerCase()
    .replace(/&/g, "")
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-+|-+$/g, "");
}
```

This differs slightly from the one in `src/lib/niches.ts` (which allows
existing hyphens through a different regex before collapsing runs) — both are
close enough in practice but not byte-identical for edge cases with existing
hyphens or multiple special characters in a row. **Use the `seed-meta.ts`
version as the reference implementation for blog post slugs**, since that's
literally what's used to create the seeded categories/authors in this
project. Slugs must be unique within their document type and, once published,
should be treated as stable (they're public URLs referenced by the sitemap
and possibly external backlinks).

### 2. Programmatic solution-page slugs (`src/lib/niches.ts`)

Completely separate system, **not Sanity-backed**. Each `Niche` has a
`slugTemplate` containing a `[city]` token, e.g.
`"gym-business-solution-website-at-[city]"`. `nicheSlug(niche, city)`
substitutes the city and runs the niche module's own `slugify()`:

```ts
export const slugify = (value: string) =>
  value.toLowerCase().replace(/[^a-z0-9\s-]/g, "").trim().replace(/\s+/g, "-").replace(/-+/g, "-");
```

`getNicheBySlug(slug)` reverses this: it builds a regex from each niche's
template (substituting `city` for a named capture group) and matches the
incoming slug against every niche in order, returning the first match plus
the extracted city segment, or `null` (→ 404) if nothing matches.
`DEFAULT_CITY = "hyderabad"` is the only city currently generated by
`allNicheParams()`/`generateStaticParams()`.

**This system is irrelevant to blog automation** — it's listed here only so
an automation doesn't accidentally conflate blog slugs with solution-page
slugs, which live in entirely different data sources (Sanity vs. a static
TS array) and have different slugify implementations.

## Practical implication for automation

When creating a post programmatically:
1. Slugify the title using the `seed-meta.ts` algorithm.
2. Check uniqueness yourself (query Sanity for an existing document of type
   `post` with that `slug.current` before creating) — Studio's
   `defaultIsUnique` check is a Studio-side UI validator and does **not**
   run automatically on a raw `client.create()`/`client.createOrReplace()` API
   call from outside the Studio.
3. Never change a slug after a post is live — it's the public URL and it's in
   the sitemap. If a title changes post-publish, keep the original slug.
